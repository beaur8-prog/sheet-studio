# 배포 운영 절차

사용자가 **배포해줘**라고 요청했을 때 GitHub 릴리즈와 리토스 공유 페이지를 갱신합니다. 일반 기능 수정은 검증·Git 커밋/푸시까지 진행하고 화면 잠금이 해제된 경우 로컬 앱을 실행합니다.

화면 잠금은 배포를 중단할 이유가 아닙니다. 잠금 상태에서는 현재 작업 중인 앱·문서를 종료하거나 교체하지 않고 배포 파일과 공유본을 갱신합니다.

## 패키지와 검증

1. 버전·설치법·수정 내역을 정리하고 Git에 커밋/푸시합니다. 버전 태그와 GitHub 초안 릴리즈를 만든 뒤 `release.yml`을 실행합니다.
2. Windows x64, Mac arm64, Ubuntu·Debian amd64를 제공합니다. 다운로드 목록과 안내 표는 Windows → Mac → Linux 순서로 표시합니다. Mac Intel 빌드는 제외합니다.
3. 세 OS의 패키지·설치 검사가 통과해야 공개합니다. 설치 파일을 다시 내려받아 manifest·SHA-256을 대조하고 Mac 앱의 서명 무결성과 실행 코드 일치를 확인합니다. 통합 `SHA256SUMS.txt`도 제공합니다.

## 리토스의 같은 링크 갱신

기존 공유 항목을 갱신합니다. **새 공유본 생성, 기존 공유 취소, 리토스/Cloudflare 재시작을 사용하지 않습니다.** 공유 주소·토큰·생성 시각·만료·읽기 전용 설정을 보존합니다. 설치 파일과 체크섬만 첨부하며 사용자 문서나 시험 자료를 포함하지 않습니다.

공개 리토스 페이지에는 **현재 배포 버전만** 표시합니다. 현재 버전의 다운로드·설치·사용법·수정 사항과 제한·경고를 유지하고, 구버전별 주요 수정·전체 버전 이력 표·과거 버전 상세 설명은 싣지 않습니다. 사용법에 남은 과거 버전 표기도 현재 동작의 설명으로 정리합니다. 전체 소스 변경 이력과 과거 문서는 Git에 보존합니다.

원본 노트·첨부를 먼저 백업한 뒤 새 버전의 설명과 검증된 파일을 준비합니다. 원본 파일을 바꾸는 것만으로 공개 스냅샷이 갱신되지는 않습니다. 화면 조작이 가능하면 **공유본 갱신**을 사용하고, 잠금 상태에서는 실행 중인 리토스의 기존 공유 백엔드 API를 호출합니다. `ShareServer.update` / `vault:updateShare`는 기존 토큰에 본문·첨부만 갱신하는 경로입니다. 공개 서버나 디스크의 공유 JSON을 직접 바꾸어 앱의 메모리 상태와 불일치를 만들지 않습니다.

0.7.16 배포에서는 기존 앱 프로세스의 지원 여부와 신호 처리기를 확인하고, 임시 loopback Inspector 연결을 통해 등록된 `vault:updateShare` 처리기를 기존 앱의 webContents/mainFrame 객체로 호출했습니다. 기존 출처 검증을 유지했으며 호출 후 임시 연결 포트를 닫았습니다. Inspector 지원이 없거나 연결이 불가능하면 앱·터널을 재시작해 우회하지 않습니다. 이 방법의 지원 여부는 [Electron 명령행 스위치](https://www.electronjs.org/docs/latest/api/command-line-switches)와 실제 설치 앱을 확인해야 합니다.

Inspector 컨텍스트의 전역 `require`가 있다고 가정하지 않습니다. `process.mainModule.require` 또는 확인된 `process.getBuiltinModule`로 필요한 모듈에 접근하고, 앱 안에 예약한 진단 콜백의 예외가 오류 대화상자를 띄우지 않도록 처리합니다. 외부 진단 클라이언트에는 시간 제한을 두고 종료 시 임시 포트가 닫혔는지 확인합니다.

마지막으로 동일한 공개 URL의 `/data`와 브라우저 화면을 확인하고, 공개 첨부를 끝까지 읽어 검증된 파일의 크기·SHA-256과 비교합니다. 설치·실행법, 현재 버전의 수정 사항, Mac 미공증·Windows 미서명·다운로드 경고와 **Windows의 PC 보호 → 추가 정보 → 실행** 안내를 유지합니다. 배포 결과와 보존한 링크를 `VALIDATION.md`에 기록합니다.
