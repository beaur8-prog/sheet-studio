## 1. 데이터 유효성 규칙 작성 (T02)

0.7.38 검증 패키지에서 데이터 탭에 규칙 작성 명령이 없음을 확인했다. 작성 창을 추가해 목록·정수·소수·날짜·시간·텍스트 길이·사용자 수식을 작성·편집하고, 입력 안내와 중지/경고/정보를 설정한다. 부분 범위 교체·삭제 시 기존 범위를 직사각형으로 나누고 상대 수식 기준점을 옮겨 다른 셀의 의미를 보존한다. 전체 열에 규칙을 설정해도 셀을 모두 생성하지 않는다.

검증: 8개 단위 시나리오, 실제 앱 작성·목록 선택·오류 수정/경고 취소·계속 입력·상대 참조 미리 채움·부분 삭제·실행 취소/다시 실행·행 삽입·XLSX 저장/재열기·작은 화면. 붙여넣기는 Excel 공식 정책에 맞게 입력 경고를 우회하는 기존 동작을 유지하고, **현재 값 검사**로 불일치를 별도 확인한다. 검사창은 읽기 전용이며 조건 불일치/확인 불가, 검사·표시 한도를 명시한다.

아직 규칙 자체를 셀 복사·채우기로 복제하는 기능은 미완료다. 보호 시트·피벗·XLSM 규칙 작성은 차단한다. 가져온 알 수 없는 속성·선택 범위 밖 규칙은 보존한다. [사용법·제한·공식 근거](DATA-VALIDATION.md).

## 2. 날짜/시간 입력의 자료형 (E01/F04/T02)

0.7.38 패키지에서 날짜 서식의 A1에 `2026-11-05`를 입력하면 숫자 날짜 46331이 아니라 문자열이 되는 것을 동일 UI 시나리오에서 재현했다. 날짜·시간 서식 또는 해당 유효성 규칙이 있는 셀의 명확한 ISO 날짜·24시간제 시각을 숫자로 저장하고, 필요한 일반 서식에는 날짜/시간 표시를 붙인다. 일반·텍스트 목적지와 따옴표·수식의 종류는 보존한다. 일반 셀의 날짜처럼 생긴 식별자를 일괄 변환하지 않는다.

검증: 4개 단위 시나리오에서 문서화된 2011-07-05=40729, 1900-02-29 특례, 1462일 차이, DST 날짜·잘못된 날짜/시각, 초·밀리초, 텍스트·값 붙여넣기 보존을 확인했다. 실제 앱은 1900/1904 각각 서식 입력·유효성 입력·오류 재시도·계산 함수·XLSX 재열기를 통과했다. 실제 Excel 입력 지역 설정 비교는 대기다.

## 3. 조건부 서식과 확장 정의 보존 (T03/IO01/F03)

2색·3색 색조와 기본 OOXML 그라데이션 데이터 막대의 작성·편집·화면·인쇄·XLSX 왕복을 연결했다. 숫자만으로 범위 기준을 계산하며 숫자인 수식·스필 결과를 포함한다. 숫자·백분율·백분위수 기준을 지원한다. 기본 막대는 문서화된 10~90% 계산을 사용하고 고급 음수 축·색은 원본 보존으로 구분한다. 단일 값·상수 분포의 실제 Excel 시각 비교는 대기다.

기존 버전에서 두 가지 결함을 추가로 재현했다.

1. 고급 데이터 막대 저장 시 기본 규칙의 `x14:id`는 남고 `x14:dataBar`·음수 색 정의는 없어졌다. 기본 규칙과 확장 정의를 함께 보존하고 범위·수식·시트 이름을 함께 갱신하도록 수정했다. 연관 없는 워크시트 확장 전체를 무작정 보존하지 않고 조건부 서식 확장만 처리한다.
2. `=SEQUENCE(3)`의 A2=2에 일반 비교 규칙을 걸어도 실제 셀 기록이 없는 배열 결과를 빈 셀로 취급해 서식이 빠졌다. 배열 계산 여부를 확인해 값에 맞게 적용한다.

ExcelJS의 기본 막대 내보내기가 빈 `x14:id`를 만들기 때문에 새 기본 막대는 유효한 기본 OOXML 규칙으로 직접 기록한다. 고급 규칙은 별도 구조를 원본에서 보존한다. 사용자 기능과 보존 범위는 [조건부 서식 안내](CONDITIONAL-FORMATTING.md)에 기록했다.

검증: 시각 규칙 단위 시나리오 8개, 원본 확장 유실·배열 서식 실패 기준 로그, 실제 앱의 작성·재계산·취소·실행 취소·인쇄용 공통 스타일·XLSX 재열기·고급 규칙 3회 저장. 고급 정의의 GUID 연결, 음수 색, 삽입으로 이동한 범위, 이름 변경 수식을 검사했다.

## 4. 표와 피벗 원본 연결 (T01/P01)

기준 코드에서 표를 A1:B3→A1:B4로 늘려 새 행 30을 추가해도 피벗 고정 범위의 합계는 30에 머무르는 것을 확인했다. 표 원본을 선택하면 표 ID·사용하는 열 ID를 기록하고 새로 고침 때 현재 범위와 이름을 읽는다. 요약 행은 제외한다. 일반 범위·가져온 고정 범위를 임의로 표에 연결하지 않는다. XLSX에는 `worksheetSource name="Sales"` 같은 실제 표 원본을 기록한다.

표 열 번호가 삭제 후 재사용되지 않도록 다음 번호를 별도로 유지한다. 사용 중인 열/표 삭제·재생성은 자동으로 다른 필드로 바꾸지 않고 오류를 알리며 마지막 결과를 유지한다. 이러한 상태의 XLSX 저장은 차단하고, 사용자가 원본을 다시 고르거나 일반 범위로 바꾸도록 한다. 유효한 XLSX를 다시 열 때는 기존 피벗 외부 변경 검사를 통과한 뒤 표 이름과 열 번호로 새 앱 ID를 연결한다.

검증: 단위 시나리오 6개와 실제 앱에서 표 안 선택→생성, 새 행 추가→합계 30→60, 열 이름 변경, 서식 유지, 고정 범위 전환·실행 취소, 새로 고침 취소 기록, XLSX 이름 원본/재열기, 열 삭제 실패 시 결과 불변, 복구를 확인했다. 기존 피벗 작성·서식 시나리오도 통과했다. 작은 화면에서는 본문만 스크롤하고 적용/취소 버튼은 유지한다. [기능 안내와 제한](PIVOT.md).

## 5. 파일 열기 취소와 단계 표시 (IO02/L01)

0.7.38 패키지에서 파일 가져오기를 대기시켜 취소 명령이 없음을 확인했다. 해석을 별도 스레드로 옮겨 현재 문서의 계산·복구 스레드와 분리하고, 취소하면 해석 스레드와 준비된 후보만 버린다. 완료 시 후보를 기존 작업 스레드에 전달한 뒤 화면에 적용한다. 형식·메타데이터·셀·개체·검증·준비 단계를 표시하고, 마지막 문서 적용 구간은 취소를 비활성화한다. 파일 크기·기록 셀 한도는 올리지 않는다.

검증: 단위 5개, 실제 앱의 해석 전·후보 준비 후 취소, Esc, 데스크톱 파일 선택 후 취소, 문서 ID·저장 폴더·복구 유지, 파싱 오류 후 바로 입력·실행 취소, 재시작 후 복구·다음 파일 열기. 실제 100,000셀 XLSX 해석 중 취소도 수행했다. 로컬 한 관측에서 취소 응답 34ms, 실제 스레드 정리 추가 약 21ms, 20ms 타이머 최대 간격 약 31ms였다. 입력 파일 SHA-256과 기존 문서는 불변이며 같은 큰 파일을 다시 정상으로 열었다. OS·장비마다 달라지는 관측값이다.

기준 패키지와 새 소스의 1,000,000셀 전체 UI 시나리오를 연속 실행했다. 둘 다 입력·정렬·필터·60개 실행 취소 유지·복구·XLSX 저장/재열기가 통과했다. 초기 단일 관측(중앙값 아님):

## 6. 숨긴 시트가 활성인 파일 열기 (IO02)

기준 패키지에서 숨긴 시트를 활성으로 기록한 정상 구조의 앱 문서를 열면 모델의 활성 시트는 숨긴 시트로 바뀌고 표시 전환은 실패하는 것을 실제 앱으로 재현했다. 첫 보이는 시트를 고르도록 수정했으며, 파일 적용 오류는 열기 트랜잭션을 되돌리고 준비된 후보도 정리한다. `hidden`/`veryHidden` 각각 앱 문서·XLSX와 이전 복구본의 활성 메타데이터를 검사했다. 숨긴 값과 상태는 보존했다.

파일창·복구·배열 입력 경합의 기존 UI 회귀도 통과했다. 현재 단위 검사는 취소 5개와 보이는 시트 선택 1개가 추가되어 총 505개다.

## 7. 후보 전달 비용 비교와 작업 스레드 실패 보호

현재 문서·복구를 맡은 스레드는 교체하지 않는다. 후보를 전달할 때 수백만 셀 개체를 다시 복제하는 대신 앱 문서와 같은 JSON 표현을 UTF-8 바이트로 전달하도록 바꿨다. 검증은 해석 스레드에서 끝내며, 수신 측 디코딩이 실패하면 현재 문서를 건드리지 않고 열기 오류로 돌려보낸다. 문자열의 잘못된 UTF-8·JSON, 한글·이모지·단독 대리 코드, 유효성 XML, 피벗 설정, XLSM 원본 바이트 해시를 검사했다.

`d250c06`의 개체 전달 기준과 바이트 전달 후보를 같은 Mac의 소스 Electron, 새 격리 프로필로 번갈아 측정했다. 자료별·방식별 5회, 총 20회이며 각 입력의 SHA-256을 고정했다. 관측 구간은 파일 선택부터 복구 저장 완료까지다.

| 숫자 | 3,937ms | 3,623ms | 약 8.0% 감소 | 937→928ms |
| 반복 한글 | 5,507ms | 5,104ms | 약 7.3% 감소 | 979→972ms |

메모리는 시작/적용/복구 단계에서만 Electron 프로세스별 working set을 합산한 **관측치**다. 숫자 최대 관측값은 약 1,134→1,125MiB, 한글은 1,240→1,253MiB였으며 순간 최대와 공유 메모리 중복을 판정할 수 없어 메모리 개선으로 주장하지 않는다. 이 결과는 전달 방식 비교이며 Excel 또는 모든 100만 셀 문서의 보증이 아니다. 최종 적용 단계의 약 1초 멈춤은 남아 있다. 측정 당시 워커 자산 해시와 20개 원시 관측을 `import-wire-benchmark.json`에 기록했다. 재현 도구는 `tests/ui-import-benchmark.mjs --compare-root=<기준 작업 폴더>`다.

추가로 원래 작업 스레드가 실패할 때 후보 준비 응답을 무한히 기다릴 수 있는 경로를 점검했다. 내부 중단 신호로 해석 스레드를 정리하고 실패 사유를 전달하며 파일 데이터 읽기 중에도 UI 대기를 해제하도록 연결했다. 단위 오류 주입으로 원래 오류 통지·후보 종료·다음 고아 해석 스레드 방지를 확인했다. 실제 OS의 메모리 부족 종료를 재현했다는 뜻은 아니다.

## 8. 차트 계열별 참조 편집 (C01/C02)

새 차트와 명시적으로 변환한 차트에서 계열 추가·삭제·이름·순서·색, 떨어진 열·다른 시트·이름 범위, 분산형 X/Y·연결선, 거품 크기, 혼합 차트 유형·보조축을 지정한다. 원본 차트는 기본 보존하고 고급 서식을 잃는 변환을 사용자가 선택한 뒤에만 편집한다. 변환 시 원래 참조를 읽으며 임의의 A1:B2로 바꾸지 않는다. 원본 XML의 부분 참조 편집은 후속이다.

검증: 11개 단위 시나리오에서 범위·길이·이름·색 거부, 동적 이름·다른 시트, 리터럴 이름, 행 삽입, 3회 XLSX 왕복을 확인했다. 커진 이름 범위의 1,000개 미리 보기 한도 표시는 기존 코드에서도 동작함을 확인하고 회귀 검사만 추가했다. 표 열은 정의된 이름을 통해 연결하며 구조화 참조를 차트 수식에 직접 새로 쓰지는 않는다. 점/연결선이 섞인 분산형은 OOXML 그룹을 분리하여 각 연결 정책을 유지한다. 실제 앱에서 두 떨어진 열의 4개 값, 취소·잘못된 범위의 문서 불변, 순서 변경과 실행 취소/다시 실행, X/Y·거품·보조축·1,000×680 화면·XLSX 재열기와 변환을 통과했다. [사용 방법과 제한](CHARTS.md).

## 9. 독립 엔진 교환에서 추가 발견한 차트 결함

LibreOffice 교환 검사를 추가해 여러 분산형 그룹이 있는 XLSX를 읽을 때 그룹 수만으로 혼합 차트로 오인함을 재현했다. 실제 그룹 유형의 집합으로 판별하고 각 계열의 선 숨김·곡선 그룹 여부를 함께 읽는다. X값을 생략한 원본은 기존 그림과 같은 1, 2, 3…을 자료 미리 보기에도 표시한다. 이 검사는 그룹·계열·참조와 계산 결과를 확인하며 곡선의 동일한 픽셀 렌더링을 의미하지 않는다.

검사 도구는 `tests/libreoffice-next-interop.mjs`다. 원본 합성 파일을 LibreOffice에서 저장한 뒤 Sheet Studio가 다시 3회 저장한다. 외부 엔진은 기본 데이터 막대를 확장 규칙으로 바꾸거나 피벗의 머리글 행·총계 문구·빈 교차 셀을 재구성할 수 있다. 이 차이는 원시 결과에 기록하고 표 원본·집계·외부 네이티브 피벗과 변경 후 보고서의 보존을 별도로 확인한다. 외부 차트 색 변경도 동일 렌더링 통과로 간주하지 않는다.

LibreOffice 26.8.0.3에서 유효성·안내 전용 규칙·시각 규칙·고급 막대·표 피벗·분산형·혼합형의 **7개 파일 교환 및 파일별 3회 후속 저장**을 통과했다. 기본 막대→확장 규칙, 피벗 배치, 분산형 두 번째 색 `#e15759`→`#99ccff` 변화는 별도 차이로 기록했다. 원본 자료·집계/차트 값·이름·X값·연결 정책을 검사했고 외부 결과와 개체의 후속 보존을 확인했다. `test-results/libreoffice-next/report.json`이 원시 결과다.

## 10. 기능을 연결한 사용자 시나리오

`ui-linked-report`에서 전체 금액 열의 유효성 규칙, 기본 데이터 막대, 표 열을 참조하는 정의된 이름 차트, 표 기반 피벗을 하나의 문서에서 사용했다. 새 행이 표·차트에 반영되고, 150을 거부한 뒤 40으로 다시 입력하여 피벗 합계가 60→100으로 바뀌었다. 새로 고침의 실행 취소/다시 실행, XLSX 저장·재열기, 앱 복구 이후에도 규칙·색 막대·차트·표와 피벗 연결이 유지됐다. 유효성 규칙은 처음부터 전체 열에 명시적으로 설정했으며 자동 복사 상속을 검증한 것은 아니다.

## 11. 20회 반복 사용 검사 (L01)

`ui-import-endurance`는 동일한 격리 프로필과 앱에서 합성 혼합 문서의 열기→셀/수식 계산→실행 취소/다시 실행→저장→새 문서→저장 파일 재열기를 20회 반복한다. 원본 파일 해시, 셀 수, 수정 값·종속 수식·마지막 셀, 해석 스레드 정리와 실행 취소 메모리 예산을 검사한다. 마지막 편집 문서를 열린 채 종료한 뒤 빈 시작과 명시적 복구를 확인한다.

10만 셀의 20회와 복구를 통과했다. 회당 전체 흐름 중앙값 약 4,985ms, 최대 5,670ms, 20ms 타이머 최대 간격 356ms였다. Electron working set 합계의 단계별 최대 관측은 약 1,236MiB이며, 시작 직후보다 초기 수회 증가 후 6–10/11–15/16–20회 종료 시점 중앙값은 1,216/1,214/1,184MiB였다. 실행 취소 추정량은 최대 132,889,298바이트로 128MiB 예산 안에 머물렀다. 이는 순간 최대 RSS·장기 누수 부재의 증명이 아니다. 100만 셀의 20회와 복구도 통과했다. 회당 전체 흐름 중앙값은 29,783ms, 최대 34,209ms, UI 최대 간격은 1,485ms였다. 단계별 working set 합계 최대 관측은 2,437MiB(약 2.38GiB)였고 5회 구간별 종료 시점 중앙값은 1,727→1,882→2,076→2,302MiB였다. 이 값만으로 누수 여부를 판정하지 않았다.

100만 셀을 별도 프로필에서 다시 20회 처리하며 5회마다 렌더러·문서 작업 스레드·메인 힙을 수집했다. 빈 문서 상태의 5/10/15회 working set은 수집 전 1,595/1,489/1,652MiB에서 수집 후 1,290/1,191/1,351MiB로 내려갔다. 렌더러 JS 사용 힙은 수집 후 6.20/6.35/6.40MiB였다. 20회는 마지막 100만 셀 문서를 유지한 다른 상태라 빈 문서 수치와 직접 비교하지 않는다. 임시 할당의 회수를 확인한 것이며 전체 프로세스의 장기 누수 부재를 증명하지 않는다. GC 노출·강제 수집은 `--gc-probe` 진단 실행에만 사용하고 제품 코드에는 추가하지 않았다. 모든 반복에서 해석 스레드는 정리됐으며 원본 해시·편집 결과·저장/재열기·빈 시작/명시적 복구가 유지됐다.

반복 관측의 Mac 패키지는 `009b6b3`(ASAR `3eb9ee5d2deda2c1e311e967b456efd370fdb4b11a7b758371fa8bf32fcc9b32`)다. 이후 차트 변환 보호·안내 전용 규칙을 보강한 최종 패키지는 별도로 관련 UI와 대용량 전체 시나리오를 검사한다. 일부 UI/단위 검사를 병행했고 OS 캐시·공유 메모리 영향을 통제하지 않았으므로 반복 시험 시간을 엄격한 성능 벤치마크나 최소 RAM 요구량으로 쓰지 않는다. 중간 대화에서 혼용한 메모리 단위는 이 문서의 **MiB** 관측값을 기준으로 한다.

초기 반복 시험은 마지막에 **새 빈 문서**를 만든 뒤 이전 편집 문서가 복구될 것이라고 잘못 기대했다. 명시적으로 새 문서를 만든 저장 상태와 차가운 시작의 빈 화면을 구분하도록 시험을 수정했다. 또한 첫 전체 Mac CI는 매우 짧은 해석 단계 표시를 Playwright 폴링이 놓쳐 실패했다. 실제 진행 DOM 변경을 관찰해 실제 취소 버튼을 즉시 활성화하도록 시험을 바꿨으며 파서 대기·속도 조작이나 제품 코드 변경은 하지 않았다. 결정적 단계별 취소 시험은 별도로 유지한다.

## 12. 미리 보기에 없는 원본 계열의 변환 손실 방지 (IO01/C01)

직전 개발 패키지에서 33계열 원본을 열고 변환하면 내부의 32계열 미리 보기만 복제하여 1계열이 빠지는 것을 실제 앱으로 재현했다. 편집 초기값을 만들 때 원본 차트 XML의 계열 수와 읽힌 계열을 비교한다. 32개를 넘거나 원본을 전부 읽을 수 없으면 자동 초기값을 비우고 명시적인 범위 재구성을 요구한다. 원본 보존 상태의 제목 등 지원 편집은 유지한다. 실제 앱의 변환 거부·문서 불변·사용자 범위 재구성·실행 취소와 원본 33계열 저장, 단위 3회 왕복을 확인했다. 이 원본 자료 3개를 추가하여 SDK 검사 대상은 57개가 됐다.

기존 축·대시보드·10종 차트 검사는 데이터 지정 방식 선택을 반영했다. 분산/거품형 시험에는 숫자 X/Y/크기를 사용하고, 임의 SVG 길이 대신 실제 데이터 점을 검사한다. 이 시험 변경을 새로운 제품 결함 수정으로 세지 않는다. 해당 묶음의 로컬 단위는 521개 중 520 통과·Windows 전용 1개 제외였고, 최종 안내 규칙 수정 후에는 522개다.

## 13. 안내 전용 규칙의 표준 유형과 자유 입력 (T02/IO01)

오류 알림 플래그가 있는 표준 `type="none"` 규칙은 입력 제한이 없어야 하지만 직전 패키지에서 미지원 규칙으로 읽어 자유 입력을 막는 것을 재현했다. 또한 앱의 **모든 값 + 입력 안내**는 내부 이름 `any`를 그대로 XML에 기록해 표준 열거값에 맞지 않았다. 읽을 때 `none`을 내부 자유 입력으로 연결하고 쓸 때 `none`으로 기록한다. 이전 개발본의 `any` 원본도 XLSX 저장 사본에서만 표준화하며 열린 문서·값은 바꾸지 않는다. [Microsoft의 OOXML 유형 정의](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.spreadsheet.datavalidationvalues)를 따랐다.

실제 앱에서 가져온 안내 규칙 자유 입력, 새 안내 작성, 구형 표기 저장 복구, 안내·숫자/문자 입력의 XLSX 재열기를 확인했다. 단위 1개와 SDK 자료 3개를 추가해 최종 단위는 522개, SDK는 60개가 됐다. LibreOffice의 7번째 안내 전용 파일 교환과 후속 저장도 통과했다. 원본의 알 수 없는 다른 유형을 임의로 바꾸지는 않는다.

## 14. 실제 PDF의 시각 규칙

`ui-conditional-print`로 최종 앱의 인쇄 UI를 거쳐 A4 한 장을 만들었다. 배경 인쇄를 켠 Chromium PDF를 Poppler 96DPI PNG로 렌더링해 전체 페이지를 확인하고 색조 끝점/중간, 막대 안/밖, 문자·논리값·빈칸 제외, 숫자 수식의 **19개 픽셀 지점**을 검사했다. 격자와 인쇄의 색·그라데이션·길이가 같고 원래 문서는 불변이었다. 이는 PDF 출력 확인이며 실제 프린터나 Excel의 픽셀 일치를 뜻하지 않는다. 재현은 `tests/ui-conditional-print.mjs`, `tests/check-conditional-print-pixels.py`다.

첫 추가 Mac CI는 시나리오가 모두 통과한 뒤 GitHub 결과 업로드 API의 시간 초과로 실패했다. 제품 코드를 바꾸지 않고 해당 작업만 재실행했다. Windows·Ubuntu 시나리오는 처음부터 통과했다. 최종 결과와 근거는 아래 표 및 로컬 원시 기록에서 확인한다.

## 16. 남은 우선순위

- **T02:** 셀 복사/채우기에 규칙 자체를 상속하고 상대 수식·숨김 셀·잘라내기·문서 간 정책을 검증한다. 현재는 대상 범위에 직접 설정한다.
- **IO02/L01:** 최종 모델 적용의 약 1초 멈춤, 저장·정렬·계산 취소, 큰 개별 서식/수식 자료의 장기 메모리를 이어서 측정한다.
- **C02/P02:** 원본 차트 XML의 안전한 부분 계열 편집, 날짜 축과 레이블, 외부 기본 피벗 필드 역변환은 미완료다.
- **T03/A01:** 아이콘·고급 음수 축 작성과 실제 Excel 시각 비교, 물리 IME·화면 읽기 검증이 남아 있다. 새 기능을 늘리기 전에 위 보존·응답성을 우선한다.

검토용 [Mac 앱·Windows 설치 파일](../release/0.7.39/)과 [검증 원시 자료](../.verification/excel-next-four-hour-20261105/)를 원래 작업 소스 `/Users/swryu/Library/Caches/SheetStudioWork/core-five-hour-20261031` 아래에 보관했다. 버전·커밋·해시·CI 주소는 검증 폴더의 `final-provenance.json`에도 기록했다. 이 파일 링크는 해당 Mac의 로컬 자료이며 GitHub에 바이너리를 공개한 링크가 아니다. 사용자 설치 앱·프로필·복구·문서·클립보드는 시험에 사용하지 않았다. 공개 배포·리토스 갱신은 별도 요청 대상이다.
