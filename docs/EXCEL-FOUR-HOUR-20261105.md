### 1차: 외부에서 변경한 피벗의 덮어쓰기 방지

- 재현: 앱이 만든 XLSX의 네이티브 피벗 집계를 합계→평균으로 바꾸고 결과 D4를 160→40으로 저장한 합성 자료를 열면, 기존 Custom XML의 합계 설정이 다시 적용돼 D4가 160으로 돌아왔다. 실제 Excel 실행 결과가 아니라 네이티브 OOXML 변경으로 재현했다.
- 원인: 가져오기에서 네이티브 정의와 앱 설정의 일치를 확인하지 않고 `applyPivot`을 실행했다.
- 변경: 새 파일에는 네이티브 배치 근거를 함께 기록한다. 기존 파일은 필드·집계·필터·원본을 대조한다. 설정이 다르거나 앱 설정이 없는 기본 피벗은 저장된 결과와 원본 피벗/캐시 연결을 보존하며 임의로 다시 계산하지 않는다. 사용자 지정 숫자 형식 ID와 패키지 관계를 저장 시 재연결한다.
- 편집: 원본 피벗은 안내 막대에 표시하고 Excel에서 새로 고치도록 안내한다. 일반 범위 변환을 명시적으로 선택하면 현재 값을 편집할 수 있고 실행 취소로 원본 개체를 복원한다. 보존 중 행열·시트·표 구성 변경은 제한한다. 외부/OLAP·슬라이서·고급 피벗 서식은 손실 가능한 XLSX 저장을 거부하고 앱 문서 또는 명시적 변환을 안내한다.
- 검증: 피벗 관련 단위 검사와 XLSX 3회 왕복, 앱 JSON 왕복·검증, 실제 Electron의 열기→편집 제한→저장→재로드→변환→편집→실행 취소 통과. 전체 단위 424개 중 423개 통과·Windows 전용 1개 제외. Windows/Mac/Linux 후속 검사는 진행 중이다.


### 2차: 찾기·바꾸기의 조건 일치와 안전한 일괄 변경

- 재현: 기존 찾기는 대소문자를 무시했으나 모두 바꾸기는 대소문자를 구분했다. `ALPHA`, `Alpha Beta`, `alpha`를 찾으면 3개가 표시되지만 모두 바꾸기는 일부만 바뀌었다. 검색 범위와 표시 값/수식 구분, 변경 미리 보기도 없었다.
- 변경: 같은 조건으로 찾기·바꾸기를 수행하고 현재 시트/선택 영역/통합 문서, 대소문자/전체 일치, 표시 값/값·수식 원문, 숨긴 시트 포함을 선택한다. 표시 값은 검색 전용이며 수식 결과를 덮어쓰지 않는다. 검색은 작업 스레드에서 수행하고 결과 목록을 제한해 큰 문서를 다시 정렬·복제하지 않는다.
- 변경 전 미리 보기를 요구한다. 여러 시트의 결과를 복사본에서 보호·배열·유효성·표 머리글/참조·용량 한도까지 검사한 뒤 한 번에 적용한다. 오류가 있으면 모든 시트를 유지하며 창 안에 원인을 표시한다. 한 번의 실행 취소/다시 실행과 원래 파일 폴더 연결을 유지한다.
- 검증: 새 단위 7개와 실제 Electron의 미리 보기→시트 간 결과 이동→일괄 변경→같은 창 재검색→실행 취소/다시 실행→선택/표시 값 검색→보호된 셀 전체 취소→XLSX 저장을 통과했다. 전체 단위 431개 중 430개 통과·Windows 전용 1개 제외. 실제 Excel UI 비교를 새로 수행한 것은 아니다.


### 3차: 알려진 파일 손실의 안내와 원본 보호

- 기준 0.7.37의 실제 입출력 모듈에서 합성 XLSX의 `xl/embeddings/document.bin`이 안내 없이 사라짐을 재현했다. 새 가져오기는 OLE/컨트롤/대화형 댓글/Data Model/슬라이서/다른 Custom XML/잘못된 XLSX의 VBA 등 판별 가능한 항목을 기록한다. 이는 모든 OOXML 기능의 전수 판별이 아니다.
- 도움말과 상태 표시줄의 파일 호환성에서 편집·원본 보존·저장 제한을 확인한다. 위험 항목이 있는 일반 XLSX 저장은 먼저 안내하며, 사용자가 선택한 기능 제외 사본은 원본 경로/동일 파일의 하드링크·심볼릭 링크에 덮어쓰지 않는다. 파일 경로는 앱의 로컬 위치 설정에서만 관리하고 내보낸 문서에 넣지 않는다.
- 앱 문서는 현재 편집 상태와 판별 결과를 저장한다. 보관하지 못한 개체의 원본 바이트까지 보존하는 형식이라고 표시하지 않는다. 복잡한 네이티브 피벗은 기존 제한을 유지하고 명시적 변환을 먼저 안내한다.
- 단위 5개와 실제 Electron의 안내→취소→원본 덮어쓰기 거부→다른 이름의 사본→앱 문서 저장을 통과했다. 원본 전체 SHA-256과 포함된 바이너리가 그대로임을 확인했다.

### 대용량 보강

- 새 바꾸기의 첫 구현에서 문서 전체를 실행 취소에 남길 수 있는 경로를 발견해 변경 셀·메타데이터만 적용하도록 수정했다. 100만 숫자/한글 셀에서 각각 20회 반복해 추가 기록은 약 4.5KB였으며 되돌리기·다시 실행과 증분 복구를 확인했다.
- 전체 셀의 깊은 복제와 배열 생성, 불필요한 격자 재계산을 줄였다. 이 Mac의 같은 합성 숫자 문서에서 처리 시간은 약 2.7초→1.8초, 20ms 화면 타이머의 최대 지연은 약 250ms→20~30ms로 줄었다. 초기 새 구현과 개선 구현의 비교이며, 모든 컴퓨터의 보장 수치나 공개 0.7.29와의 직접 비교가 아니다. 최종 측정의 중앙값·메모리·조건은 종료 시 정리한다.

### 4차: 대화상자와 수식의 문서화된 경계

- 대화상자 공통 처리에서 조합 중 Enter/Esc·229 키가 적용/닫기를 실행하지 않도록 하고, 최초 포커스·Tab 경계·닫힌 뒤 편집 포커스를 보강했다. 합성 composition 이벤트의 실제 Electron 검사와 기존 찾기·셀 서식 흐름을 통과했다. Mac 화면은 잠겨 있어 OS 창 전환 검사는 제외했으며 셀 서식의 나머지 검사와 파일 저장 검사는 통과했다.
- XLOOKUP 첫 인수 생략이 0으로 처리돼 실제 빈 셀보다 숫자 0을 선택하는 사례를 재현했다. [Microsoft 규칙](https://support.microsoft.com/en-us/excel/functions/xlookup-function)에 따른 물리적 빈 셀 검색을 일반/전체 행열 경로에서 보강한다. 실제 Excel의 빈 문자열·오류·이진 검색 전체 조합은 검증하지 않았다.
- LibreOffice 26.8의 캐시를 의도적으로 틀리게 넣은 격리 비교에서 물리적 빈칸/0과 빈 문자열의 차이를 확인했다. 일부 빈 문자열 조합은 엔진 간 차이가 남아 실제 Excel 대조 대기로 유지하며 이를 Excel 정답률에 합산하지 않는다.
- [Excel 찾기/바꾸기](https://support.microsoft.com/en-gb/excel/get-started/find-or-replace-text-and-numbers-on-a-worksheet?nochrome=true), [Range.Replace 조건](https://learn.microsoft.com/en-us/office/vba/api/excel.range.replace), [피벗 구조](https://learn.microsoft.com/en-us/office/open-xml/spreadsheet/working-with-pivottables)를 참고했다. 지원 범위를 넘어서는 기능의 새 Excel 실행 검증을 했다는 의미는 아니다.

### 5차: 피벗 서식과 필터 행 위치

- 기존 새로 고침은 셀 서식·크기를 모두 새로 만들었다. 항목·머리글별 서식과 크기 유지 옵션을 추가하고, 실제 Electron에서 사용자 지정 숫자 코드·색·열 너비→원본 수정→새로 고침→실행 취소/다시 실행→옵션 해제와 실행 취소→XLSX 저장·재열기를 점검한다.
- 보고서 필터 때문에 XLSX에서 내려간 행 위치를 가져올 때 셀/행 기본 서식과 조건부 규칙 범위도 함께 되돌린다. 3자리 숫자 코드에 생성 기본값 2자리가 다시 섞이던 후속 저장 결함을 왕복 검사에서 발견해 수정했다. 필터 있는 XLSX의 서식·메모·행열 크기·조건부 범위를 3회 왕복하는 단위 검사를 추가했다.
- 같은 앱 피벗의 바깥에 추가한 F10 셀이 가져오기에서 지워지던 사례를 재현했다. 이 경우 원래 배치를 보존하고 F10은 계속 편집하게 한다. 외부 캡션·스타일 변경도 보존한다. 메모를 지울 수 있는 필터 갱신은 전체 취소한다.
- 현재 전체 단위는 **448개 중 447개 통과·Windows 전용 1개 제외**다. 이전 피벗 수정 `1738630`의 [전체 편집 CI](https://github.com/beaur8-prog/sheet-studio/actions/runs/41950633814)는 Mac·Windows·Ubuntu에서 통과했다. 이후 변경은 별도 전체 재검증 대상으로 유지한다.

### 6차: 표의 오른쪽 열 추가와 범위 확장

- 기존 코드는 아래 행 추가만 구현했고 표 관리에서도 열 수 변경을 거부했다. 오른쪽의 기존 표 행에 입력한 연속 열을 포함하고 명시적 오른쪽 범위 확장을 추가했다. 넓은 아래쪽 붙여넣기는 기존 열 폭으로만 행을 확장한다. [Microsoft의 확장 규칙](https://support.microsoft.com/en-us/excel/resize-a-table-by-adding-or-removing-rows-and-columns-in-excel)을 기준으로 구현했으며 머리글 패턴 추론은 포함하지 않는다.
- 새 머리글 이름·열 ID·계산 열·새 열 필터를 기존 모델에 연결한다. 다른 표·병합·배열·보호·요약 행의 기존 자료 충돌을 확인한다. 새 요약 위치에 자료가 있으면 명시적 크기 변경 전체를 거부한다. 표 크기 창의 열 축소는 여전히 행·열 삭제 명령으로 안내한다.
- 관련 단위 17개와 실제 Electron의 중복 머리글 입력→열 추가→실행 취소/다시 실행→새 계산 열→명시적 확장→병합 충돌 유지→새 열 필터→XLSX 저장/재열기→복구를 통과했다. 기존 표 편집 전체 시나리오도 재실행했다. 사용자 클립보드는 쓰지 않았으며 붙여넣기의 자료 계획은 단위·CI에서 별도 검사한다.

### 7차: 차트 삽입 전 데이터 확인과 빈 셀 처리

- 설정만 보고 삽입해야 하던 창에 작업 스레드의 그림·계열/항목/값 표·실제 원본 참조를 추가했다. 가로 숫자 4개의 포함, 원형의 첫 계열/도넛의 고리, 분산·거품형 좌표, 캐시·1,000개 표시 제한을 안내한다. 작은 화면에서는 한 열로 배치한다. 미리 보기 취소는 문서나 실행 취소를 만들지 않으며 서로 다른 SVG clip ID를 사용한다.
- 빈 셀의 간격/0/선 연결을 기본 꺾은선·방사형·분산형·혼합에 연결하고, 표식 전용 분산형의 선 연결은 비활성화한다. 물리적 빈 셀만 대상으로 삼고 오류·텍스트·빈 문자열 수식을 자동 변환하지 않는다. 날짜 정렬·숨김 마스크 후에도 빈 위치를 함께 이동한다. 기본 방사형에서 빈 값을 0으로 연결하던 표시도 수정했다. 새/원본 XLSX의 `dispBlanksAs`, 구형 앱 문서의 원본 설정을 읽고 보존한다. XLSM의 미지원 설정 변경은 저장 시 명시적으로 거부한다.
- 차트 단위 **54개**와 실제 Electron의 숫자 4개/유형/잘못된 범위/취소/원본 참조/명시적 변환/좁은 창, 빈 셀 3개 옵션/오류/수식 빈 문자열/실행 취소/원본 XLSX 옵션 수정/복구를 통과했다. 기존 범위 선택·축 설정 실제 앱 검사도 통과했다. [Microsoft 설명](https://support.microsoft.com/en-us/excel/display-empty-cells-null-n-a-values-and-hidden-worksheet-data-in-a-chart)에 있는 채널별 `#N/A` 옵션은 별도 대기 항목이다.

### 8차: 보존 경계와 큰 표의 메타데이터 복제

- 사용자 지정 피벗 스타일 이름만 남고 정의가 사라지는 XLSX를 재현했다. 이 경우 고급 서식 보존 저장을 거부하고, 앱 문서에 원래 스타일 XML까지 함께 보관한다. 구형 앱 메타데이터의 네이티브 결과 시작 위치도 확인하여 외부에서 F5:I8로 옮긴 피벗을 A1:D4로 되돌리지 않는다.
- 0행 결과는 네이티브 피벗이 없는 정적 셀 예외다. 결과 바깥에 F10을 추가하거나 기존 0을 999로 고친 파일을 열 때도 과거 앱 설정으로 덮어쓰지 않도록 실제 정적 결과를 대조한다. 복원을 보류한 경우 안내 막대를 표시하며 현재 셀은 편집·저장할 수 있다.
- 손실 사본의 원본 경로를 알 수 없거나 원본이 사라진 경우, 다른 이름의 기존 파일이 같은 파일의 하드링크일 수 있어 새 파일 이름만 허용한다. 일반 저장은 유지한다. 줄바꿈을 포함한 합법적인 파일 이름 때문에 호환성 정보가 앱 문서를 무효화하던 사례도 수정했다.
- 표가 하나라도 있으면 일반 셀 하나를 바꿀 때도 모든 보존 수식 메타데이터를 복제하는 경로를 재현했다. 실제 표 머리글 이름 변경 때만 그 복제를 수행하고 나머지는 변경 셀만 남긴다. 250,000개 수식·메타데이터의 1회 자료 계획 관측은 약 812→272ms, 추가 heap은 약 83→30MB였다. 이는 Node의 합성 계획 단계이며 실제 사용자 전체 지연의 보장 수치가 아니다. 반복 관측은 최종 증거에 남긴다.
- 같은 재현의 전/후 검사와 실제 Electron 정적 결과 보존·편집·저장을 통과했다. 현재 단위는 **469개 중 468개 통과·Windows 전용 1개 제외**다.

### 독립 엔진 비교

LibreOffice **26.8.0.3**의 격리 프로필로 합성 XLSX 7개를 열고, 일부 수식 캐시를 -999로 바꾼 뒤 실제 재계산·재저장했다. 확장한 표의 열 ID·계산식·메모, 필터 있는 피벗의 합계, 외부 평균 피벗의 정의·결과, 차트 3개 빈 셀 정책, 생략 인수 XLOOKUP의 빈칸/0 선택과 1900/1904 양쪽의 백분율·빈 날짜·ISBLANK·COUNT를 확인했다. 원본 파일 SHA-256은 모두 유지했다.

첫 비교에서는 외부 피벗의 D4가 40→100으로 보여 차이로 기록했다. 네이티브 위치와 셀을 조사하니 LibreOffice가 머리글을 추가해 보고서를 A1:D4→A1:D5로 바꾸었고 평균 총합계 40은 D5에 있었다. 네이티브 결과 범위의 총합계로 대조한 후에는 값 차이가 없었고 Sheet 재저장에서도 위치·40을 유지했다. 첫 주소 비교 기록과 수정된 의미 비교 기록을 모두 보관한다. 이는 새 Microsoft Excel/VBA 실행 검증이 아니다.

### 9차: 혼합 문서 생성 검사에서 발견한 표시·빈 날짜

- 고정 난수 `0x51ee738`로 두 시트의 값·문자 숫자·논리·오류/오류 문자열·수식·1900/1904 날짜·메모·서식·차트 유형/빈 셀 설정을 섞고, 통합 문서 바꾸기와 실행 취소/다시 실행을 거쳐 XLSX를 두 번씩 저장/재열었다. 첫 사례에서 백분율의 표시가 저장 전 0.125→재열기 12.50%로 바뀌는 문제를 발견했다.
- 백분율 직접 입력과 일반 텍스트 붙여넣기는 입력한 소수 자릿수를 표시 형식으로 연결한다. 명시적인 일반/텍스트/숫자 형식과 초기화·보호된 셀 서식, 값만 붙여넣기의 원래 데이터 타입은 유지한다. 구형 앱 문서의 암시적 백분율도 화면·필터·차트·XLSX에서 같은 형식을 사용한다.
- 그다음 검사에서 날짜 서식이 있는 빈 `<c/>`를 0으로 복원하는 경로를 재현했다. 워크시트 날짜 원문 복원에서 빈 문자열에 `Number('')`를 적용하던 것이 원인이었다. 실제 숫자 0과 빈 날짜를 구분하며 메모·ISBLANK·COUNT를 1900/1904 양쪽 파일에서 3회 왕복해 확인했다.
- 수정 후 **120개 문서 / 240회 XLSX 왕복**을 통과했다. 표시·값·오류 종류·메모·차트 자료와 실행 취소를 확인한 자체 일관성 검사이며 Microsoft Excel 실측으로 분류하지 않는다. 실제 Electron의 백분율 입력→일반 형식 변경→실행 취소/다시 실행→텍스트 입력→빈 날짜/숫자0 저장·재열기와 기존 사용자 지정 숫자 형식·서식 초기화 검사도 통과했다.
- 전체 단위 **471개 중 470개 통과·Windows 전용 1개 제외**, 업데이트 엔진 **29개 통과**. 파일 원본과 실제 클립보드는 검사 대상으로 쓰지 않았다.

### 메모리 반복 관측

250,000개 보존 수식과 표 하나에서 일반 셀 한 개를 바꾸는 자료 계획+차이 생성 단계를 `d48b4c3`와 개선 소스로 번갈아 5회씩 관측했다. 각 회차 전 GC를 요청한 같은 Node v26.5.0/Mac arm64 환경의 중앙값은 **약 840→262ms**, 추가 heap **약 113→31MiB**였다. 창 조작·작업 스레드 전송·저장 전체의 사용자 지연을 뜻하지 않는다. 숫자/한글 100만 셀 UI의 기존 20회 관측과 완성 앱의 장시간 반복은 별도 기록한다.

### 10차: 배열 계산이 입력 도중 끝날 때 남는 편집 상태

- 최종 Mac 전체 CI에서 `ui-array-races`의 다음 파일 열기가 시간 초과됐다. 실패 화면에는 배열 결과 A2에서 거부된 `x`의 편집 상태가 남아 있었다. 단순 재시도 성공으로 끝내지 않고, 실제 작업 스레드의 계산 응답만 잠시 보류해 `수식 확정 → 결과 셀 입력 시작 → 계산 완료 → Enter` 순서를 고정했다. 수정 전 완성 앱에서 동일하게 실패했다.
- 계산 중 Enter 경로는 편집을 안전하게 취소했으나, 입력 도중 계산이 끝나면 일반 확정 경로가 변경만 거부하고 편집을 유지했다. 확정 시 원래 셀의 편집 가능 여부를 다시 검사해 새 배열 결과 셀의 입력만 취소한다. 데이터 유효성의 정상 오류 수정 흐름과 배열 밖의 한글 입력은 유지한다.
- 같은 응답 순서의 실패→통과, 다음 문서 열기, 배열 밖 한글 유지와 기존 즉시 입력·2차원 결과·붙여넣기·저장·복구 전체 시나리오를 통과했다. 최종 소스를 다시 빌드하고 플랫폼 검사를 수행한다.

## 완성 앱의 100만 셀 반복 관측

Mac arm64·16GiB 환경, 완성 앱 소스 `d829200`에서 숫자 문서와 반복 한글 문서를 각각 100만 셀로 구성했다. 100회씩 작업 스레드 찾기→한 셀 바꾸기 후 마지막 실행 취소/다시 실행·복구를 검사했다. 이후 `773d05f`는 배열 결과 셀 편집 종료만 수정한 소스이며 이 100회 측정을 다시 수행했다고 표시하지 않는다.

두 경우 마지막 실행 취소 60개·약 13.2KB를 유지했고 반복 변경한 셀의 되돌리기·다시 실행을 확인했다. 복구는 자동 저장 완료 후 추가로 쓸 셀 묶음이 0개였다. 기존 기록이 60개 한도로 밀려난 뒤의 음수 “추가 기록 바이트”를 메모리 절감으로 해석하지 않는다.

### 혼합 문서의 열기·저장·문서 전환 20회

최종 앱 코드 `773d05f`의 완성 Mac 앱으로 매회 **100,000셀**의 숫자·긴 한글·백분율·수식·논리·실제 오류·오류 문자열·빈 날짜·숫자0·메모·서식을 가진 합성 문서를 열었다. 1900/1904 날짜 기준을 번갈아 사용했다. 셀 수정→종속 수식 확인→실행 취소/다시 실행→실제 XLSX 파일 저장→재열기→처음/끝 행·종류·메모 확인→새 문서 확인을 20회 통과했다.

한 회 중앙값 **4,619ms**, 최댓값 **5,852ms**였다. 강제 GC 없이 다시 열기/새 문서 직후 working set 합계는 **675–1,299MiB**, 마지막 **1,108MiB**로 관측됐다. 실행 취소의 128MiB 예산에 맞춰 마지막에는 8개 기록·약 127.77MiB를 유지했다. 기록이 한도까지 쌓이는 정상 증가와 메모리 누수를 구분하며, 이 20회만으로 모든 문서의 누수 부재를 보장하지 않는다.

글꼴 순서 수정 후 `f7043f7` 완성 앱에서 **같은 20회 전체를 재실행해 통과**했다. 이번 관측은 중앙값 **3,802ms**, 최댓값 **3,950ms**, working set 합계 **978–1,520MiB**, 마지막 **1,400MiB**였다. 워밍업·GC와 OS 캐시 조건이 다르므로 앞 관측보다 빨라진 원인을 글꼴 수정으로 단정하지 않는다.

### 11차: 독립 SDK가 발견한 XLSX 글꼴 요소 순서

- [첫 SDK 검사](https://github.com/beaur8-prog/sheet-studio/actions/runs/41969246150)는 합성 12종의 최초 저장+재저장2회 **36개 파일** 모두에서 `styles.xml/font`의 `sz` 위치 오류를 보고했다. 표·차트·피벗 자체의 오류가 아니라 공통 글꼴 순서였다. LibreOffice와 자체 읽기가 허용한 파일도 SDK 검사에서는 실패할 수 있음을 확인했다.
- ExcelJS 4.4의 `FontXform`이 자식 요소를 일부 알파벳 순서로 출력하는 것을 확인했다. [공식 SDK 3.5.1의 CT_Font 정의](https://github.com/dotnet/Open-XML-SDK/blob/v3.5.1/generated/DocumentFormat.OpenXml/DocumentFormat.OpenXml.Generator/DocumentFormat.OpenXml.Generator.OpenXmlGenerator/schemas_openxmlformats_org_spreadsheetml_2006_main.g.cs)에 맞춰 최종 XLSX의 글꼴 요소 순서만 정리한다. 값·서식 ID·알 수 없는 확장 내용과 관련 없는 바이너리는 유지한다. 순서가 이미 맞는 파일은 다시 압축하지 않는다.
- 고급 글꼴 속성·리치 텍스트·차등 서식·확장·바이너리 유지, 3회 왕복과 기존 보존 검사를 통과했다. 전체 단위 **473개 중 472개 통과·Windows 전용 1개 제외**다. 같은 36개 파일의 SDK 검사와 최종 플랫폼·패키지 검사를 다시 실행한다. 실제 Excel 실행이나 복구 경고의 재현이라고 표시하지 않는다.

- [수정 후 SDK 검사](https://github.com/beaur8-prog/sheet-studio/actions/runs/41969871153), `f7043f7`: **36개 모두 오류 0개**, 검사 전/후 원본 파일 해시 유지. 같은 120개 합성 문서의 240회 XLSX 왕복과 LibreOffice 7개 사례도 최종 소스로 다시 통과했다.
- 같은 100,000셀 혼합 모델의 전체 XLSX 내보내기를 전/후 소스로 번갈아 5회씩 관측했다. 중앙값은 `773d05f` **371.5ms**, `f7043f7` **370.0ms**였다. 이 표본에서 20% 이상 악화는 없었으며 UI 전체 시간·최악 메모리·모든 파일의 보장 수치를 뜻하지 않는다. 고급 조건부 글꼴의 차등 서식 개수도 5회 왕복 동안 1개로 유지했다.
